# 资产节点界面评审

> 日期：2026-10-09
> 对象：保存和读取资产的节点界面。代码在 `js/assetLibraryUI.js`、`nodes/assets/nodes.py`、`nodes/assets/server.py`。
> 先前的可行性评估是 `docs/ASSET_LIBRARY_UI_EVALUATION.md`（方案 B：下拉；方案 C：弹窗预览，当时定为二期）。当前实现把 B 和 C 叠在了一起。
> 本文只评界面。不改代码。

## 结论

现在这套界面不够完善，不能算方便，也不能算合适。前端扩展、动态下拉、批量选择弹窗都已经有了，方向是对的。问题是同一个选择被做了三遍，保存节点选中已有名字之后不会把库里的正文带出来，图片接口把整张原图塞进浏览器。

目标界面只要做三件事：

1. 保存：选「新建」或「覆盖同一个类型的已有名字」。覆盖时先把库里的正文和缩略图填进节点，再改。没接新图、没接新音频时，保留磁盘上的原文件。
2. 单个读取：一个名字下拉，旁边一块缩略图和一行摘要。摘要来自接口，不排队。
3. 批量读取：节点上一条可排序的缩略图条，点「选择资产」打开卡片。顺序就是 `<Picture N>`。`names` 文本继续当序列化真相，但默认收起来。

执行路径保持现在这样：下拉和预览走 HTTP，不进 `IS_CHANGED`，不进 prompt。缩略图单独缓存，不参与图缓存键。

## 节点上现在实际有什么

七个资产节点都会跑 `js/assetLibraryUI.js`。`library_dir` 被藏起来，空字符串表示本机默认库（`$MIE_ASSET_LIBRARY`，否则 `~/mie_asset_library`）。每个节点末尾追加不序列化的按钮。

| 节点 | 用户看得见的控件 | 真正写进工作流的值 |
|---|---|---|
| Save Character / Save Scene | 名字下拉、大段多行正文、图像/音频插座、条件出现的 `new_name`、两个按钮 | `library_dir`、`name`、正文、`new_name` |
| Load Character / Load Scene | 名字下拉、刷新按钮 | `library_dir`、`name` |
| Load Asset Batch | 多行 `names`、最多 10 个槽位下拉、选择弹窗按钮、刷新按钮 | `library_dir`、`names` |
| List Character / List Scene | 一个刷新按钮。列表要排队之后才出现在输出里 | `library_dir` |

序列化策略是对的：后加的按钮和槽位都是 `serialize: false`，老工作流的 widget 下标不会错位。列表请求按目录合并成一个在途 Promise，这也是对的。

## 不方便的地方

### 保存会把没看见的正文写回去

保存节点的下拉只换 `name`。选中「夏栀」时，`appearance` / `voice` / `description` 保持节点上原来的字，经常是空的，或者是上一个角色留下的。队列一跑，`save_character` 用这些字覆盖磁盘。空正文会在校验处报错；非空但属于别人的正文会静默写进这个名字。

界面上没有任何一步展示「将要覆盖的是哪一段、哪张图」。使用说明把「选了已有名字」解释成明确的覆盖意图。意图有了，内容没有从库里读回来。没有 `GET` 元数据接口，前端也读不到正文，只能读到名字列表和整张 PNG。

图像和音频插座仍是必填。改一个词也要重新接一张图和一段音频，否则存不进去。这是保存界面最重的一步，单靠下拉消不掉。

### 保存角色的下拉里混进了场景

`SaveCharacterAsset` 的前端配置是 `kinds: ["both"]`。`entriesFor` 因此把角色名和场景名都放进同一个下拉。选一个场景名再保存，会在 `characters/` 下新建同名角色。批量读取碰到两个树里同名的条目会直接报错。保存场景的下拉只列场景，两边不对称。

名字框的占位文案仍是「先填 library_dir，下拉自动出现」。第六次修订之后空目录是合法的默认库，这句会让人以为还没配好。

### 批量读取用三套控件编辑同一份名单

`names` 多行框、槽位下拉、图片弹窗，三处都写同一串名字。槽位每次变更都删掉全部槽位 widget 再新建（`rebuildSlots`，而且是在下拉的 callback 里调用的）。LiteGraph 会因此重算节点高度，打开着的菜单会被拆掉。九个槽位的 CPU 开销不大，操作手感差。

弹窗已经能按卡片追加和删除。槽位下拉是同一功能的第二份，还把显示值写成 `[角色] 名字`。扫描还没回来时，未知名字一律标成角色，和磁盘上的类型可能不一致。写回 `names` 时前缀被剥掉，类型信息并不在序列化结果里。

已选中的卡片再点一次没有任何提示。同名角色和场景在弹窗里是两张卡片，点下去写进 `names` 的是同一个裸名字，执行期才会报「既是角色又是场景」。

槽位不能拖动排序。顺序就是 `<Picture N>`，现在只能删掉再按新顺序重选。

### 库目录只活在一条会消失的提示里

「📁 库目录」把隐藏的文本框翻出来，并用 toast 显示解析后的路径。toast 几秒就没了。节点上没有常驻的一行「当前库：C:\Users\...\mie_asset_library」。七个节点各自藏一份路径，用户无法确认它们是不是同一个库。

List 节点的刷新按钮把扫描结果放进 `node.__mieAssets`，节点上不画任何名字。不排队就看不到列表，刷新按钮像是坏的。下拉已经能列出名字之后，List 节点不该再占主路径；它若留下，刷新就应该在节点上画出名字和被跳过的目录原因。

### 扫描成功之后下拉不会自己变

保存节点执行成功、或者在资源管理器里新放了一个目录，前端缓存仍是上一次的名字列表。缓存只在点「🔄」或弹窗里的刷新时用 `force: true` 丢掉。保存完本节点的下拉里还没有这个新名字。

`debounceTimer` 是整个页面一个变量。在节点 A 里改路径，会清掉节点 B 还没发出的刷新。

## 性能

执行图本身没有被前端拖慢。`IS_CHANGED`、内容哈希、队列里的 PNG/WAV 编解码都没走这套 JS。要守住的是：预览永远不要做进读取节点的执行函数。

会拖慢界面的是图片接口：

- `GET /mie_nodes/assets/picture` 把 `portrait.png` / `scene.png` 整文件读进内存再返回，`Content-Type: image/png`。
- 弹窗为每张卡片设 `img.src`。`loading="lazy"` 只能推迟请求，不能把一张 2K PNG 变成缩略图。二十个角色打开一次选择器，浏览器要解码二十张原图。这是打开弹窗时主线程卡顿的原因。
- `Cache-Control: max-age=60`，URL 只有目录、名字和类型。覆盖保存之后六秒到六十秒内，同一 URL 仍是旧图。服务端注释写「文件一变 URL 就变」，代码里没有 mtime 或内容哈希。

名字列表接口只返回名字，这个边界要保持。不要把图片字节塞进 `/mie_nodes/assets/list`。列表会读每个资产的 JSON 做校验，几十到几百个资产是毫秒级，可以留在刷新和节点创建时调用。同一目录的多个节点已经共用一个 Promise，不要改成每个节点各扫一次。

缩略图应另开接口，例如最长边 256、JPEG 或 WebP、大约几十 KB。缓存键用源文件的大小和 mtime，URL 带上这个键，覆盖后浏览器自然换图。缓存放在库目录外的临时目录或进程内存里，不要写进资产目录，也不要参与 `character_cache_key`。弹窗关闭时不必取消已经完成的解码；不要在打开时预取音频。

槽位条改成一个 DOM widget 之后，改顺序只改 DOM 和隐藏的 `names` 字符串，不再增删 LiteGraph widget，节点高度稳定。这比继续重建十个 combo 更轻。

## 建议的界面

仍用现在的扩展入口和 `serialize: false` 的附加控件。不新做侧栏资产管理器，不做搜索页。检索仍然不做，做的是节点上的输入辅助。

### 保存角色 / 保存场景

节点从上到下：

1. 常驻一行：`库：解析后的绝对路径`。点击才展开路径框。七个节点同一行样式。
2. 名字：下拉只含本类型已有名字，第一项是「新建…」。选「新建…」才显示 `new_name`。
3. 选中已有名字后，请求一份元数据（名字、类型、appearance 或 description、voice、图片 mtime），把正文填进框，旁边显示缩略图。框里的字和库里不一致时，节点上标「将覆盖」。
4. 图像插座、音频插座改为可选。没连接时覆盖保存沿用磁盘上的 PNG / 音色样本；新建时仍然必填。这一条是 Python 行为，不是只改 JS 能完成的。不做这一条，改一句描述就必须重接一张图。
5. 多行框给一个固定的小高度。不要在没选名字时展开两大块空白。

保存成功后作废该目录的列表缓存，并刷新画布上使用同一目录的资产节点。

### 读取单个角色 / 场景

名字下拉只列本类型。选中后同一块预览：缩略图、正文第一行、音色有无。预览失败不影响队列；队列仍走现有的 `load_character` / `load_scene`，输出完整 IMAGE 和 AUDIO。不要在下拉变化时解码音频。播放按钮可以以后再加，点击才请求音频。

### 批量读取

去掉槽位 combo。保留隐藏的多行 `names` 作为唯一序列化字段，节点上默认不展示，菜单里留「编辑名字列表」给手改旧工作流。

节点主体是一条横条：缩略图、序号、名字、类型。拖动排序，点 ✕ 删除。按钮打开现有弹窗。弹窗改用缩略图 URL；超过一屏时用本地名字过滤，不再发请求。已在条上的卡片显示序号，再点给出提示，不追加。角色和场景同名的条目在列表里标成不可选，并写明原因，不要等到执行。

条的顺序写回 `names`，一行一个裸名字。类型不写进这串文本，避免前缀和磁盘不一致。

### 列出节点

不作为日常入口。刷新时在节点上画出扫描到的名字，以及 `status` 里被跳过的目录。不做缩略图墙。

## 不该做的

- 不要用类级 combo 替代按节点取列表。库目录是实例值，`INPUT_TYPES()` 拿不到。
- 不要上 ComfyUI 的 MultiCombo。评估里已经写明它的远程选项在 0.38 上不好驱动，本仓库其他扩展走的是 legacy widget。
- 不要为了预览去改 `Load*` 的 `IS_CHANGED` 或在执行函数里生成缩略图。
- 不要把选择器做成侧栏或独立管理页。删除、改名继续用文件管理器。
- 图片接口继续走 `validate_library_dir` 和 `validate_name`。不要接受任意文件路径。

## 验收

在本地 ComfyUI 里用鼠标走完，不手打资产名：

1. 空 `library_dir` 的新节点上能看见解析后的默认库路径。
2. 新建一个角色，再覆盖它的一句 appearance，不重接图像和音频，磁盘上的 PNG 和样本不变，JSON 里的句子变了。
3. 覆盖前，节点里看到的是这个名字当前的正文和脸，不是空白，也不是上一个角色的字。
4. 保存角色的下拉里没有场景名。
5. 批量节点选两个角色加一个场景，拖动把场景放到槽位 1，`roster_json` 的 slot 与条上的序号一致。同名的角色和场景无法被选中。
6. 打开有大约二十张定妆图的选择器时，界面不解码二十张原图。覆盖保存后立刻再打开，看到的是新图。
7. 2026-10-09 之前只在 `names` 里手写名字的工作流，加载后条上的顺序与原文一致，队列结果不变。
